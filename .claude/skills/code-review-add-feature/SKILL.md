# 기능 구현 완료 후 코드리뷰

`superpowers:requesting-code-review` 를 이 저장소 규칙에 맞춰 쓰는 스킬이다.

**왜 필요한가:** superpowers 의 리뷰어 템플릿은 일반론이다("에러 처리 됐나", "테스트 있나"). 이 저장소에서 리뷰가 놓치면 가장 비싼 두 가지는 그 일반론에 안 걸린다. 둘 다 **빌드도 린트도 테스트도 잡아주지 않는다.** 리뷰어가 안 잡으면 조용히 통과하고, 다음 사람이 틀린 문서를 믿는다. 그래서 체크 항목을 프롬프트에 직접 넣는다.

## 1. 리뷰 범위(SHA) 확정

```bash
git status --porcelain
git merge-base HEAD origin/main   # 기본 브랜치가 develop 이면 그쪽
git rev-parse HEAD
```

- **커밋 안 된 변경이 있으면 먼저 사용자에게 알린다.** 리뷰어는 `BASE..HEAD` diff 만 본다. 워킹 트리 변경은 범위에 없어 통째로 빠진다. 무엇이 안 커밋됐는지 보여주고 "커밋하고 진행 / 커밋된 것만 리뷰" 중 고르게 한다. **임의로 커밋하거나 stash 하지 않는다.**
- `BASE_SHA` — 기능이 시작된 지점. 브랜치 하나가 기능 하나면 `merge-base`. 사용자가 시작 커밋을 말했으면 그걸 쓴다.
- `HEAD_SHA` — `git rev-parse HEAD`.
- 둘이 같으면 리뷰할 커밋이 없다. 멈춘다.

## 2. 리뷰어 디스패치

```
Skill(skill: "superpowers:requesting-code-review")
```

그 스킬의 `code-reviewer.md` 템플릿을 채워 `general-purpose` 서브에이전트에 넘긴다. 스킬이 안 잡히면 템플릿은 superpowers 플러그인의 `skills/requesting-code-review/code-reviewer.md` 에 있다.

| 자리 | 채울 것 |
|---|---|
| `{DESCRIPTION}` | 무엇을 구현했는지 몇 줄. **세션 히스토리를 붙이지 않는다** — 리뷰어는 결과물을 봐야지 내 사고 과정을 볼 필요가 없다 |
| `{PLAN_OR_REQUIREMENTS}` | 계획 파일 경로, 없으면 사용자 요청 원문 |
| `{BASE_SHA}` / `{HEAD_SHA}` | 1단계 값 |

**내가 직접 diff 를 읽고 리뷰하지 않는다.** 코디네이터가 diff 를 읽으면 이어서 수정할 컨텍스트를 태운다. diff 는 리뷰어 컨텍스트에서 살고, 나한테는 지적만 돌아온다.

## 3. 저장소 규칙 블록 — 반드시 붙인다

템플릿의 `## What to Check` **다음에** 아래를 그대로 넣는다. 이게 이 스킬의 전부다. 빼면 그냥 superpowers 를 부른 것과 같다.

````
## 이 저장소의 규칙 (일반 체크리스트보다 우선한다)

리뷰 전에 저장소 루트의 CLAUDE.md 를 읽어라. 아래는 그 두 절의 요약이고,
요약과 CLAUDE.md 가 어긋나면 CLAUDE.md 가 맞다.

### 1. 테스트 정책 — 서비스 레이어 only (CLAUDE.md "Testing: TDD, service layer only")

- 새 테스트가 `<Domain>ServiceTest` 밖에 있는가? 매퍼 테스트·컨트롤러 테스트는
  정책 위반이다. 도메인 패키지당 ServiceTest 하나가 전부이고, 컨텍스트 스모크
  테스트만 예외다.
- 서비스 테스트가 매퍼를 목킹했는가? `mapper/*.xml` 의 SQL 은 이 테스트 말고
  커버리지가 없다. 목킹하면 "서비스가 메서드를 호출했다"만 검증되고 SQL 은
  아무도 안 본다. 실제 DB + `@Transactional` 이 맞다.
- 컨트롤러가 입력 검증·에러 매핑·분기 판단을 하는가? 그 로직은 이 정책 아래에서
  테스트가 닿지 않는다. 컨트롤러는 라우팅과 응답 성형까지고, 판단은 서비스로
  내려야 한다. 이건 스타일 지적이 아니라 커버리지 구멍이다.
- 테스트 없이 들어온 서비스 로직이 있는가? 실패하는 테스트가 먼저다.

### 2. okf/ 지식 번들 동시 갱신 (CLAUDE.md "Knowledge bundle (`okf/`)")

`okf/` 를 빌드하거나 테스트하거나 린트하는 것이 아무것도 없다. 코드와 **같은
변경에서** 갱신하지 않으면 낡은 채로 조용히 남고, 다음 사람이 그걸 믿고 틀린다.

diff 를 아래와 대조하라. 왼쪽이 diff 에 있는데 오른쪽이 같은 diff 에 없으면
**Important 이상**으로 보고하라.

| diff 에 이게 있으면 | 같은 diff 에 이게 있어야 한다 |
|---|---|
| 테이블 DDL, 또는 컬럼의 의미 변경 | `okf/tables/<table>.md` — 스키마 표 **와** DDL 블록 둘 다 |
| 매퍼 SQL, 또는 어느 레이어가 그 테이블을 읽고 쓰는지 | 그 테이블 문서의 `# Access` 절 |
| 엔드포인트의 경로·메서드·요청 바디·상태 코드 | `okf/api/<resource>.md` |
| 시큐리티 설정 | 영향받는 모든 엔드포인트 문서의 `# Authentication` 절 |
| 테이블 또는 엔드포인트 추가 | 새 문서 **와** 그 디렉터리의 `index.md` |

- 수정된 okf 문서는 `generated.at` 이 갱신되고, 더는 유효하지 않은 `verified`
  항목이 제거돼 있어야 한다. 그 항목들은 지금 없는 내용에 대한 확인서다.
- 반대 방향도 본다: 코드 변경이 okf/ 를 틀리게 만들지 않았다면 안 건드린 게 맞다.
  내용 변화 없이 타임스탬프만 올라간 문서는 그 자체로 지적 대상이다.
````

## 4. 지적 처리

- **Critical** — 바로 고친다.
- **Important** — 진행 전에 고친다. **okf/ 누락은 여기다.** "나중에 문서 정리"는 안 온다.
- **Minor** — 기록만 하고 넘어간다.
- 리뷰어가 틀렸으면 근거를 대고 반박한다. CLAUDE.md 를 안 읽었을 수 있으니 어느 절인지 짚어준다.
- 고친 범위가 크면 새 SHA 로 다시 돌린다. 리뷰는 싸고, 틀린 문서는 비싸다.

지적을 다 처리한 뒤 결과를 요약할 때 **두 규칙 각각에 대한 판정을 한 줄씩 남긴다.** "테스트: ServiceTest 2건 추가, 위반 없음 / okf: `okf/api/orders.md` 갱신됨". 리뷰어가 그 항목을 아예 안 다뤘으면 그것도 그대로 적는다 — 통과한 것과 확인 안 한 것은 다르다.

## 하지 말 것

- 3단계 규칙 블록 없이 리뷰어를 띄우기. 그러면 이 스킬은 존재 이유가 없다.
- 더러운 워킹 트리에서 그냥 진행하기. 커밋 안 된 변경은 SHA 범위 밖이라 리뷰에서 통째로 빠진다.
- 범위를 맞추려고 임의로 커밋·stash 하기. 사용자에게 묻는다.
- 코디네이터가 직접 diff 를 읽고 리뷰하기. 리뷰어 서브에이전트의 일이다.
- 규칙 요약을 CLAUDE.md 에서 복사해 이 파일에 더 채워 넣기. 한쪽이 바뀌면 다른 쪽이 썩는다. 위 요약은 리뷰어가 무엇을 찾을지 알 정도까지고, 근거는 CLAUDE.md 다.
- okf/ 갱신을 "나중에" 로 미루기. 그 나중은 없다.
