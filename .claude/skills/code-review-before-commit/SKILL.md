# 커밋 전 로컬 변경분 리뷰

`/pr-review-toolkit:review-pr` 을 로컬 워킹 트리에 붙이는 스킬이다.

**왜 필요한가:** review-pr 은 범위를 `git diff --name-only` 로 잡는다. 그건 *언스테이징된 tracked 파일*만 나온다. 이미 `git add` 한 파일과 아직 추적 안 되는 신규 파일이 통째로 빠진다. 커밋 직전에는 그 둘이 오히려 변경의 대부분이다. 이 스킬은 범위를 먼저 확정해서 넘긴다. 나머지는 review-pr 이 한다.

## 1. 범위 확정

```bash
git rev-parse --git-dir >/dev/null   # 실패하면 git repo 가 아니다. 멈추고 알린다.
git status --porcelain
```

`git status` 한 번이면 세 종류가 다 나온다:

| 상태 코드 | 뜻 | review-pr 기본 범위 |
|---|---|---|
| `M `, `A `, `D `, `R ` | 스테이징됨 | **빠짐** |
| ` M`, ` D` | 언스테이징 | 잡힘 |
| `MM` | 둘 다 | 언스테이징분만 |
| `??` | untracked 신규 | **빠짐** |

전부 리뷰 대상이다. 사용자가 범위를 좁혀 말하지 않았으면 좁히지 않는다.

## 2. 노이즈 제외

리뷰 가치가 없는 파일은 뺀다. 에이전트마다 락파일을 읽으면 그만큼 실제 코드에 쓸 컨텍스트가 줄어든다.

- 락파일 — `pnpm-lock.yaml`, `package-lock.json`, `yarn.lock`, `*.lock`
- 빌드 산출물 / 생성 코드 — `dist/`, `build/`, `.next/`, `*.min.*`, `*.generated.*`
- 바이너리 — 이미지, 폰트, 아카이브

**무엇을 뺐는지 결과에 한 줄로 적는다.** 조용히 빼면 사용자는 리뷰됐다고 믿는다.

남은 파일이 0개면 "리뷰할 변경이 없다" 한 줄로 끝낸다.

## 3. 통합 diff 파일 만들기

에이전트가 여럿이다. 각자 `git diff` 를 다시 돌리면 낭비이기도 하지만, 무엇보다 **각자 다른 범위를 보게 된다.** 한 번 만들어 경로를 넘긴다.

```bash
DIFF=$(mktemp -t review-diff)
git diff HEAD -- <2단계에서 남은 tracked 파일들> > "$DIFF"
```

- `git diff HEAD` 여야 한다. `git diff` 는 스테이징분을, `git diff --cached` 는 언스테이징분을 빼먹는다. 둘을 합쳐 보여주는 건 `HEAD` 기준뿐이다.
- 커밋이 하나도 없는 저장소(`git rev-parse HEAD` 실패)면 diff 를 만들지 않는다. 모든 파일이 신규 파일이다.
- **untracked 파일은 diff 에 안 들어간다.** 경로 목록으로 따로 넘기고 에이전트가 파일 전체를 읽게 한다. 신규 파일은 파일 전체가 곧 diff 다.

## 4. review-pr 실행

```
Skill(skill: "pr-review-toolkit:review-pr", args: "all parallel")
```

`simplify` 는 빼고 부른다. code-simplifier 는 리포트를 내는 게 아니라 **파일을 직접 고친다.** 리뷰 중인 diff 가 리뷰 도중에 바뀌면 사용자가 무엇을 커밋하는지 알 수 없게 된다. 사용자가 명시적으로 요청하면 리뷰가 다 끝난 뒤 따로 돌린다.

review-pr 은 자기 3단계에서 `git diff --name-only` 로 범위를 다시 잡으려 한다. **그 단계를 건너뛰고** 아래 블록을 각 에이전트 프롬프트에 그대로 넣는다. 이걸 빠뜨리면 1~3단계가 통째로 무의미해진다.

```
리뷰 대상. git diff 를 다시 돌리지 말고 아래만 본다:
- 통합 diff (staged + unstaged 합본): <DIFF 경로>
- 신규 파일 — diff 에 없으므로 파일 전체를 읽을 것:
    src/foo/new-thing.ts
- 전체 변경 파일 목록:
    ...
```

## 5. 결과 정리

에이전트 리포트를 이어 붙이지 않는다. **표 하나로 합친다.** 두 에이전트가 같은 걸 지적하면 한 줄로 합치고 지적한 에이전트를 병기한다.

```markdown
## 커밋 전 리뷰 — 파일 7개

**판정: 커밋 보류** — 블로커 2건

| # | 심각도 | 위치 | 문제 | 해결 방안 |
|---|--------|------|------|-----------|
| 1 | 🚫 블로커 | `src/a.ts:42` | 락 없이 카운터 증가 | 트랜잭션 안으로 이동 |
| 2 | 🚫 블로커 | `src/b.ts:8` | catch 에서 에러 삼킴 | 로깅 후 재throw |
| 3 | ⚠️ 중요 | `src/c.ts:17` | 신규 분기에 테스트 없음 | 빈 배열 케이스 추가 |
| 4 | 💡 제안 | `src/d.ts:31` | 중복 헬퍼 | `utils/parse` 재사용 |

리뷰: code-reviewer, silent-failure-hunter, pr-test-analyzer
제외: `pnpm-lock.yaml`
```

심각도 기준 — 애매하면 한 단계 낮춘다. 블로커에 노이즈가 섞이는 순간 표 전체가 안 읽힌다.

- 🚫 **블로커** — 구체적 실패 시나리오를 쓸 수 있고(어떤 입력/상태 → 어떤 잘못된 결과), 그 실패가 버그·데이터 손상·보안 문제로 이어진다.
- ⚠️ **중요** — 지금 안 고치면 곧 문제가 된다. 커밋 자체는 막지 않는다.
- 💡 **제안** — 취향·리팩터링. 표 아래쪽에 몰아둔다.

**판정은 블로커 개수로만 정한다.** 블로커 0건이면 "커밋 가능"이다. 중요·제안이 몇 개든 상관없다.

위치는 반드시 `파일:줄`. "인증 로직 부근" 은 위치가 아니다.

## 파일은 고치지 않는다

이 스킬의 산출물은 표다. 수정은 사용자가 따로 요청할 때 한다. 리뷰 결과를 보고 바로 고치기 시작하면, 사용자가 검토하려던 diff 가 리뷰한 diff 와 달라진다.

## 하지 말 것

- review-pr 의 기본 `git diff` 범위를 그대로 쓰기. 스테이징된 파일과 신규 파일이 빠진다. 이 스킬을 쓰는 이유 자체가 사라진다.
- `git add -N` / `git add` / `git stash` 로 범위를 맞추기. 사용자 인덱스를 건드리면 안 된다. 읽기만 해도 전부 된다.
- 에이전트 리포트 여러 개를 그대로 이어 붙여 출력하기. 길어지면 안 읽힌다.
- 블로커가 없는데 표를 채우려고 제안을 승격하기.
- 커밋하거나 푸시하기. 이 스킬은 리뷰까지다.
