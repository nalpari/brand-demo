com.eland.brand

코딩 컨벤션

이 저장소의 코드가 실제로 어떤 모양인지를 적은 문서다. 규칙을 새로 만든 게 아니라 src/ 를 읽어 이미 예외 없이 지켜지고 있는 것만 옮겨 적었고, 항목마다 근거가 되는 파일과 줄을 달았다. 리뷰에서 “이건 왜 이렇게 썼냐”는 질문이 나올 만한 지점만 다룬다.

강제하는 도구가 없다 린터도 포매터도 설정되어 있지 않다. 아래 규칙을 검사해 주는 건 아무것도 없고, 지금까지는 사람이 기존 코드를 보고 맞춰 왔다. 그래서 이 문서가 필요하다.

이 문서가 다루지 않는 것

한 사실은 한 곳에만 둔다. 아래는 각자의 자리가 있으니 여기서 반복하지 않는다.

알고 싶은 것볼 곳
빌드·테스트 명령, 테스트 배치 정책, MyBatis 함정, Boot 4 패키지 이동, 보안 현황 CLAUDE.md
테이블 컬럼과 의미, 엔드포인트 계약과 상태코드 okf/
런타임 구조 한눈에 보기 docs/diagrams/

왜 CLAUDE.md 는 매 세션 전체가 읽히는 파일이라 짧게 유지해야 하고, okf/ 는 계약의 단일 출처다. 여기에 그 내용을 복사하면 두 곳이 서로 다르게 썩는다.

서식

Java 와 XML 은 탭, YAML 은 스페이스 2칸

Spring Initializr 기본값을 그대로 쓰고 있고 8개 자바 파일 전부 예외가 없다. 에디터가 탭을 스페이스로 바꾸지 않는지 확인할 것.

여는 중괄호 다음 줄과 닫는 중괄호 앞 줄은 비운다

클래스든 인터페이스든, 8개 자바 파일 전부 그렇다.

public class SampleService {

	private static final int PAGE_SIZE = 50;
	…

}

import 는 최상위 패키지별로 묶고 그룹 사이를 빈 줄로 나눈다

그룹 안은 알파벳 순. 순서는 java.* → org.* → 그 외 (tools.*, com.*). 테스트에서는 static import 가 맨 위.

  • SampleController.java:3–17
  • BrandApplication.java:3–11

와일드카드 import 를 쓰지 않는다

SampleController 는 org.springframework.web.bind.annotation 에서 10개를 개별로 가져온다.

가시성

클래스는 public, 생성자와 @Bean 메서드는 package-private.

public class SampleService {
	SampleService(SampleMapper mapper) {   // public 아님
		this.mapper = mapper;
	}
}

왜 스프링은 리플렉션으로 호출하므로 public 이 필요 없고, 좁은 가시성이 “이건 컨테이너가 부르는 것”이라는 신호가 된다.

  • SampleService.java:19
  • SampleController.java:25
  • SecurityConfig.java:14
  • BrandApplication.java:36

생성자에 @Autowired 를 붙이지 않는다

생성자가 하나면 스프링이 알아서 쓴다. 운영 코드의 의존성은 private final 필드 + 생성자 주입이고, 필드 주입은 쓰지 않는다.

테스트만 @Autowired 필드 주입을 쓴다

스프링 테스트도 생성자 주입이 되긴 하지만, 이 저장소는 필드 주입으로 통일되어 있다.

  • SampleServiceTest.java:23

테스트 클래스·메서드와 헬퍼는 좁게

테스트 클래스와 테스트 메서드는 package-private — JUnit 5 는 public 을 요구하지 않는다. 클래스 내부 헬퍼는 private (SampleService 의 requireName).

상수

숫자에 이름을 붙여 클래스 맨 위에 private static final 로 둔다. 항목 사이는 빈 줄로 띄운다.

private static final int PAGE_SIZE = 50;

private static final int MAX_NAME_LENGTH = 20;

계산식이 의미를 더 잘 드러내면 계산식 그대로 둔다

MAX_REQUEST_BODY_BYTES = 8 * 1024 는 8192 보다 읽기 쉽다.

  • BrandApplication.java:16

에러 메세지에 값을 다시 적지 말고 상수를 넣는다

"name must be at most " + MAX_NAME_LENGTH + " characters"

왜 상한을 바꿀 때 메세지가 같이 따라온다. 값을 문자열에 박아 두면 둘이 어긋난 채로 배포된다.

없음을 다루는 방식

이 프로젝트에는 @RestControllerAdvice 도 DTO 도 없다. 그래서 “없는 행”과 “잘못된 입력”이 각각 어디서 어떤 모양으로 처리되는지가 고정되어 있다.

상황서비스컨트롤러결과
행이 없음 null 반환
findById, update		 ResponseEntity.of(Optional.ofNullable(…)) 404
삭제 대상 없음 false 반환 notFound().build() 404
입력이 잘못됨 ResponseStatusException 던짐 아무것도 안 함 400 + RFC 9457
일어나면 안 되는 일 IllegalStateException 던짐 아무것도 안 함 500

“없음”은 예외가 아니라 null

서비스는 조회 실패에 예외를 던지지 않고 Optional 을 반환하지도 않는다. 컨트롤러가 감싼다.

  • SampleController.java:36

입력 검증은 서비스에서 던진다

컨트롤러에 검증을 두면 이 프로젝트의 테스트 배치 정책상 테스트할 방법이 없다. spring-boot-starter-validation 이 의존성에 없으므로 @Valid 도 쓸 수 없다.

400 과 500 을 구분해서 던진다

호출자가 고칠 수 있으면 ResponseStatusException, 코드나 DB 상태가 잘못된 것이면 IllegalStateException.

왜 후자를 400 으로 던지면 우리 버그를 사용자 잘못으로 보고하게 된다.

  • SampleService.java:34–36

에러 메세지는 영어 소문자 평서문

"name is required", "name must not contain NUL". 이 문자열은 API 응답의 detail 로 그대로 나가므로 사용자에게 보이는 문구다. 바꾸면 okf/api/samples.md 도 같이 고친다.

검증 가드

여러 조건을 검사할 때는 비용이 낮은 검사를 먼저 둔다.

private void requireName(String name) {
	// 길이 먼저 — 이 아래는 20 코드포인트 이하가 보장된 문자열만 본다
	if (name != null && name.codePointCount(0, name.length()) > MAX_NAME_LENGTH) { … }
	if (name == null || name.replaceAll("[\\p{Z}\\p{C}]", "").isEmpty()) { … }
	if (name.indexOf('\0') >= 0) { … }
}

왜 replaceAll 은 호출마다 정규식을 컴파일하고 결과 문자열을 새로 만든다. 길이 검사가 뒤에 있으면 익명 호출자가 보낸 거대한 문자열이 그 비용을 전부 치른 뒤에야 400 이 된다.

  • SampleService.java:51–62

트랜잭션

@Transactional 은 쓰기 메서드에만 붙인다. create, update, delete 에 있고 findPage, findById 에는 없다. 읽기 전용 조회에 트랜잭션을 열 이유가 없다.

왜 update 처럼 “쓰고 나서 다시 읽어 반환”하는 메서드는 반드시 트랜잭션 안에 있어야 같은 트랜잭션의 변경을 읽는다.

테스트

테스트를 어디에 두는지는 CLAUDE.md 가 정한다. 여기서는 어떻게 쓰는지만 다룬다.

AssertJ 만 쓴다

JUnit 의 assertEquals / assertTrue 계열은 저장소에 한 번도 등장하지 않는다. assertThat, assertThatThrownBy 를 static import 로 가져온다.

메서드 이름은 문장으로 쓴다

동작과 기대가 둘 다 들어간다.

createRejectsBlankName
findPageHoldsFiftyRowsAndTheCursorAdvancesPastThem
deletingARowBeforeTheCursorDoesNotSkipTheNextPage

왜 testCreate1, createTest 같은 이름은 실패했을 때 무엇이 깨졌는지 알려주지 못한다.

상태코드는 이 관용구로 검증한다

assertThatThrownBy(() -> service.create(sample(" ")))
	.isInstanceOf(ResponseStatusException.class)
	.extracting(e -> ((ResponseStatusException) e).getStatusCode())
	.isEqualTo(HttpStatus.BAD_REQUEST);

왜 예외 타입만 보면 400 과 404 를 구분하지 못한다. 둘 다 ResponseStatusException 이다.

영향 범위는 무고한 행으로 증명한다

“하나를 바꿨더니 하나만 바뀌었다”를 확인하는 방법이다.

Sample created = service.create(sample("before"));
Sample bystander = service.create(sample("bystander"));
…
assertThat(service.findById(bystander.getId()).getName()).isEqualTo("bystander");

생성 헬퍼는 private 로 클래스 맨 아래에

SampleServiceTest 의 sample(String name).

테스트는 실제 DB 를 쓴다

매퍼를 목으로 대체하지 않는다. 이유는 CLAUDE.md 에 있다.

커밋 메세지

영어 type 접두사 + 한글 subject. git log 전체가 이 형식이다.

feat: /api/samples 에 keyset 페이지네이션과 입력 상한 추가

익명으로 호출되는 엔드포인트라 전체 목록 조회도 무제한 name 도
그대로 부하가 된다. …
  • type: feat fix refactor style docs chore test
  • subject 50자 이내, “무엇을 했는지”
  • body 는 선택이지만, 왜 그렇게 했는지를 적을 값이 있으면 적는다. 무엇을 했는지는 diff 가 이미 말해준다.
  • 커밋은 파일이 아니라 의도 단위로 나눈다. 한 줄로 설명되지 않으면 두 개다.

코드를 바꿀 때 같이 해야 하는 것

okf/ 번들은 아무것도 빌드하지 않고 아무것도 검사하지 않는다. 그래서 코드와 어긋나도 조용히 틀린 채로 남는다. 무엇을 바꿨을 때 무엇을 고쳐야 하는지는 CLAUDE.md 의 표에 있다. PR 을 올리기 전에 그 표를 확인할 것.

근거는 src/ 를 직접 읽어 확인했다. 코드가 바뀌어 이 문서와 어긋나면, 문서가 아니라 먼저 코드를 보라 — 이 문서는 관찰의 기록이지 명령이 아니다.
